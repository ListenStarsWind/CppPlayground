# 类和对象_课时4

## 静态成员

### 静态成员变量

类中的数据成员可以用 `static` 声明为静态数据成员。非静态数据成员属于具体的对象，不同对象各有自己的数据成员；静态数据成员属于类本身，同一个类的对象访问的是同一个静态数据成员。

即使没有创建任何对象，静态数据成员也可以存在。它的存储期通常贯穿整个程序的运行过程，适合记录整个类共同维护的状态，例如已经创建了多少个对象。

补充一点：静态数据成员也可以使用 `thread_local`，这时每个线程有自己的一份。线程是操作系统中的概念，如果还没有学过，这里先跳过即可，不影响后面的学习。

看下面一道题目：实现一个类，这个类中包含着若干接口，可以输出已经实例化的对象个数和正在使用的对象个数。

在下面这个示例中，只提供了默认构造函数和拷贝构造函数。每次成功构造时，累计数和存活数各加一；析构时，只让存活数减一。这样就能分别得到累计创建的对象数和当前存活对象数。

**A.h**

```cpp
#pragma once

namespace wind {
class A {
    // 重置计数器
    friend void resetCounters();

    // 读取私有计数器
    friend void out(int& totalCreatedCount, int& liveObjectCount);

   public:
    A();
    A(const A& object);
    ~A();

   private:
    static int _totalCreatedCount;  // 重置以来累计创建的对象数
    static int _liveObjectCount;    // 当前存活的对象数
};

void resetCounters();
void out(int& totalCreatedCount, int& liveObjectCount);
void CopyAndDestroy(const A& source);
void info();
}  // namespace wind
```

**A.cpp**

```cpp
#include "A.h"

#include <iostream>

namespace wind {
// 定义静态数据成员
int A::_totalCreatedCount = 0;
int A::_liveObjectCount = 0;

A::A() {
    _totalCreatedCount++;
    _liveObjectCount++;
}

A::A(const A& object) {
    (void)object;
    _totalCreatedCount++;
    _liveObjectCount++;
}

A::~A() {
    _liveObjectCount--;
}

// 仅在没有存活的 A 对象时调用
void resetCounters() {
    A::_totalCreatedCount = 0;
    A::_liveObjectCount = 0;
}

// 使用输出型参数返回两个计数器的值
void out(int& totalCreatedCount, int& liveObjectCount) {
    totalCreatedCount = A::_totalCreatedCount;
    liveObjectCount = A::_liveObjectCount;
}

void CopyAndDestroy(const A& source) {
    // 临时对象在函数调用期间保持存活
    std::cout << "3" << std::endl;
    info();

    A tmp = source;

    std::cout << "4" << std::endl;
    // 拷贝构造使两个计数器各加 1
    info();

    (void)tmp;
}

void info() {
    int totalCreatedCount = 0;
    int liveObjectCount = 0;
    out(totalCreatedCount, liveObjectCount);
    std::cout << "累计创建的对象数: " << totalCreatedCount << std::endl;
    std::cout << "当前存活的对象数: " << liveObjectCount << std::endl;
}
}  // namespace wind
```

**main.cpp**

```cpp
#include <iostream>

#include "A.h"

void test1() {
    std::cout << "1" << std::endl;
    // 此时还没有创建对象
    // 两个计数器均为 0
    wind::info();

    wind::A m;
    wind::A n;

    std::cout << "2" << std::endl;
    // 通过默认构造函数创建了两个对象
    wind::info();
    wind::CopyAndDestroy(wind::A());

    {
        wind::A o;
        std::cout << "5" << std::endl;
        // 临时对象和它的副本已经析构; 此时 o 已经构造
        wind::info();
    }

    std::cout << "6" << std::endl;
    // 对象 o 已经析构
    wind::info();

    wind::A p;
    wind::A q;

    std::cout << "7" << std::endl;
    // 再通过默认构造函数创建两个对象
    wind::info();
}

int main() {
    test1();
    std::cout << "8" << std::endl;
    // test1 中的局部对象都已析构
    wind::info();
    return 0;
}
```

3

4

几个关键位置的计数变化如下：

| 位置 | 刚发生的事情                       | 累计创建 | 当前存活 |
| ---- | ---------------------------------- | --------:| --------:|
| 1    | 还没有创建对象                     | 0        | 0        |
| 2    | 创建 `m`、`n`                      | 2        | 2        |
| 3    | 创建临时对象，绑定到 `source`      | 3        | 3        |
| 4    | 用 `source` 拷贝构造 `tmp`         | 4        | 4        |
| 5    | `tmp` 和临时对象已析构，又创建 `o` | 5        | 3        |
| 6    | `o` 离开作用域                     | 5        | 2        |
| 7    | 创建 `p`、`q`                      | 7        | 4        |
| 8    | `test1` 中剩余的四个对象都已析构   | 7        | 0        |

`CopyAndDestroy(wind::A())` 中的临时对象绑定到引用参数，直到包含这次调用的完整表达式结束才析构；函数内部的 `tmp` 则在函数返回时析构。示例中的 `resetCounters()` 没有被调用：静态计数器在程序开始时已初始化为零。这个函数只是提供按需重置的接口，只有没有存活的 `A` 对象时才能将两个计数都清零，否则后续析构会使存活数失真。重置后，累计数表示的是重置以来创建的对象数，而不再是整个程序运行以来的总数。

### 友元函数与名字查找

上面的两个计数器是类的私有成员，普通的类外函数不能直接访问它们。为了让 `resetCounters` 和 `out` 能读取或修改计数器，我们在类中用 `friend` 声明了这两个函数：

```cpp
friend void resetCounters();
friend void out(int& totalCreatedCount, int& liveObjectCount);
```

友元函数不是类的成员函数，但它可以访问授予友元关系的类的私有成员。因此，`out` 能读取 `A` 的计数器，`resetCounters` 也能修改它们。友元声明可以写在类中的任何访问区域，权限不因声明处于 `public` 或 `private` 而改变。友元函数可以在类外定义，也可以在类内定义；它始终不是成员函数，没有隐式的 `this` 指针。

再看 `A.h`：除了类内的友元声明，类外还在命名空间中声明了同名函数。为什么要写两次？回答这个问题之前，先看看编译器怎样查找一个名字。

我们知道，源文件中使用 `#include` 包含头文件时，预处理器会把头文件的内容展开到包含位置。经过预处理后，原本分散在源文件和头文件中的声明、定义和调用等内容，就进入了同一份供编译器处理的代码。

这份经过预处理、交给编译器编译的代码，称为**翻译单元**。一个源文件通常对应一个翻译单元；多个源文件各自经过预处理和编译，之后再由链接器将它们产生的目标文件组合起来。

虽然声明和调用进入了同一个翻译单元，但这并不意味着编译器处理调用时，只需要随意地从整份代码中找一个同名声明。

可以先建立一个近似的模型：编译器大体上沿着翻译单元自上而下处理代码。当它遇到一条声明时，会分析并记录这条声明提供的信息，例如名字、类型、所属作用域，以及它与其他声明之间的关系。此时，编译器并不知道后面是否一定会用到这个名字，但这些信息需要被保留下来，以便后续分析使用。

例如：

```cpp
int global_value;

namespace wind
{
    void resetCounters();

    class Date
    {
    private:
        int year_;
    };
}
```

从作用域的角度看，我们可以把其中的关系想象成一种层级结构：

```
全局作用域
├── global_value
└── 命名空间 wind
    ├── 函数 resetCounters
    └── 类 Date
        └── 成员 year_
```

在这个模型中，全局作用域里既有直接声明的东西，也有命名空间；命名空间里可以有函数、类，也可以有更深一层的命名空间；类里面又有自己的成员。这样组织之后，当后面需要查找某个名字时，就可以结合名字所在的位置和限定范围，确定应该考虑哪些声明。

不过，这只是从**检索和作用域关系**出发建立的直观模型，并不是说编译器内部一定使用了这样一棵树。实际编译器为了完成语法分析、类型检查、名字查找、生成代码等不同工作，很可能同时使用多种数据结构，从不同角度记录和组织同一份代码的信息。

数据结构没有脱离用途的“最好”。需要完成的操作不同，适合采用的组织方式也会不同。这里用树状结构来理解层级关系，是根据已有的计算机知识作出的合理推测；具体编译器怎样实现，还需要查阅它的源码或相关资料才能确认。

另外，“大体上自上而下处理”适合用来建立初步认识，但不必把它理解为编译器只能从头到尾扫描一次、绝不能回头。编译器内部可以分阶段处理信息；C++ 对某些位置的名字可见性也有特殊规则。我们目前关注的是：**声明提供的信息会被编译器记录和组织起来，后续分析代码时再按照语言规则使用它们。**

当编译器处理到函数调用时，它就需要利用这些信息，找到调用所指向的函数声明。例如：

```cpp
wind::resetCounters();
```

这里写出了 `wind::`，编译器就按照限定名查找的规则，在 `wind` 命名空间中查找 `resetCounters`。它不会因为翻译单元里其他命名空间也有名为 `resetCounters` 的函数，就把它们全部拿出来参与这次查找。

换句话说，**名字查找有确定的规则和范围**。我们可以把编译器内部的组织方式想象成有助于局部检索，但语言规则首先决定的是哪些声明有资格被找到；具体怎样高效实现，则由编译器决定。

如果找到多个同名函数，编译器还需要结合实参类型进行重载决议，从候选函数中选择合适的版本；如果找不到可用函数，或者无法选出唯一的最佳函数，就会报错。

#### 友元声明为什么还需要在类外再写一次

理解名字查找之后，再看这段代码：

```cpp
namespace wind
{
    class A
    {
        friend void resetCounters();
    };

    void resetCounters();
}
```

类内的这条声明：

```cpp
friend void resetCounters();
```

声明了函数 `resetCounters`，同时赋予它访问类 `A` 私有成员的权限。虽然声明写在类里面，但这里声明的 `resetCounters` 并不是 `A` 的成员函数，它属于外层的 `wind` 命名空间。

不过，友元声明有一条特殊的名字查找规则：如果一个函数首次出现在类内的友元声明中，那么它的名字不会因此自动对普通名字查找可见。

也就是说，编译器处理类定义时，已经记录了这个函数以及它与 `A` 的友元关系；但之后遇到：

```cpp
wind::resetCounters();
```

不能仅靠那条类内友元声明，通过普通的限定名查找找到它。

因此，我们在 `wind` 命名空间中再声明一次：

```cpp
void resetCounters();
```

这样，`resetCounters` 的名字就能够被普通查找找到。后面的 `wind::resetCounters()` 可以直接在 `wind` 中找到这条声明；至于 `resetCounters` 为什么有权访问 `A` 的私有成员，依据仍然是类内的友元声明。

两条声明对应的是**同一个函数**，不会因为写了两次就产生两个函数。它们分别建立了友元关系，并让函数名对普通查找可见。

这也说明，我们以前对声明的理解可以再扩展一步：同一个函数可以有多条声明，声明所处的位置和写法不同，产生的作用也可能不同。所以，说这里存在重复声明是对的，但重复声明不一定多余。

#### 为什么 `Date` 的流运算符没有类外声明也能使用

并非所有首次在类内声明的友元函数，都必须在类外再声明一次。函数调用还有一种补充查找方式，叫作**实参依赖查找（ADL）**：编译器可以根据实参的静态类型，确定相关的查找范围，寻找候选函数。

例如（此处只展示声明，实际使用还需要包含 `<ostream>`，并提供运算符定义）：

```cpp
namespace wind
{
    class Date
    {
        friend std::ostream& operator<<(std::ostream& out,
                                        const Date& d);
    };
}
```

当外部代码使用：

```cpp
wind::Date d;
std::cout << d;
```

编译器知道 `d` 的静态类型是 `wind::Date`。在处理 `<<` 时，实参依赖查找会考虑与 `Date` 关联的范围，并且有一条特殊规则允许它找到关联类中声明的友元函数。于是，即使头文件中没有再写一条类外声明，编译器仍然可以找到这个 `operator<<`。

对比最初的两个友元：

```cpp
friend void resetCounters();
friend void out(int& totalCreatedCount, int& liveObjectCount);
```

`resetCounters()` 没有实参，`out(...)` 的实参都是内置类型。调用它们时，编译器无法根据这些实参关联到类 `A`，也就不能通过这条路径找到类内声明的友元。因此，如果希望外部代码通过普通方式调用它们，就需要在命名空间作用域补充声明。

这里的普通查找、实参依赖查找和重载决议都是**编译期间**的工作。函数被选定后，运行时不需要再按照这些规则重新搜索声明。

### 静态数据成员的声明与定义

看过友元函数后，我们再回到两个计数器。`A.h` 中的类定义声明了它们，`A.cpp` 又写了一次：

```cpp
int A::_totalCreatedCount = 0;
int A::_liveObjectCount = 0;
```

为什么不能只写类内的声明？要回答这个问题，需要先认识单一定义规则。

#### 单一定义规则

单一定义规则（One Definition Rule，简称 ODR）是一组关于定义的规定。我们已经知道，声明让编译器知道名字和类型；定义则提供实体或具体内容。同一个名字可以在不同位置声明多次，但定义不能随意重复。

对于例子中的非内联静态数据成员，类内的 `static int _liveObjectCount;` 是声明；程序使用这个计数器时，需要一处对应的定义。我们把定义写在 `A.cpp` 中，`main.cpp` 和其他源文件通过头文件知道它的声明，最后由链接过程把使用和定义联系起来。如果没有提供所需的定义，通常会在链接时报未定义；如果在多个源文件中分别给同一个成员写定义，则会违反规则，通常表现为重复定义的链接错误。

这里的“一个定义”针对程序中的同一个实体，而不是说整个程序只能有一条定义语句：不同的变量当然各有各的定义。此外，类定义等内容可以按规则出现在多个翻译单元中；后面介绍的内联变量也有相应的多翻译单元规则。

标准中还有“ODR 使用”这个术语。以静态常量成员为例：

```cpp
class Limits {
public:
    static const int size = 10;
};

int values[Limits::size];
const int* address = &Limits::size;

const int Limits::size;
```

`Limits::size` 的类内声明提供了常量值。定义数组时，编译器使用这个值确定长度，这里的用法不需要再为它提供类外定义。取地址则不同：`&Limits::size` 需要访问这个变量本身，属于 ODR 使用，所以要有最后那条类外定义。这里列举的是两种具体情形；ODR 使用的完整判断还有更多细节，后面遇到时再展开。

回到计数器：程序会实际读取和修改它们，所以需要定义。

#### 为什么在类外定义？

在 C++11 及更早的标准中，普通静态数据成员的类内声明不是定义。被 ODR 使用时，需要在类外提供定义。C++17 中如果仍采用非内联的普通静态成员，这一点同样适用。

```cpp
class A {
private:
    static int _totalCreatedCount;
    static int _liveObjectCount;
};

// 在类外定义静态成员
int A::_totalCreatedCount = 0;
int A::_liveObjectCount = 0;
```

为什么要这样规定？

我认为，从传统的编译、链接模型来看，这种设计其实相当自然。

类的定义负责描述一个类拥有哪些成员。对于普通的非静态数据成员，其存储空间属于具体的类对象；而静态数据成员则不同，它们独立于具体对象存在，由同一个类的所有对象共享。

因此，类内的静态数据成员声明，可以理解成一种类似 `extern` 的声明：它告诉编译器，这个类存在这样一个静态变量，明确了变量的名称、类型及其所属的类，但并没有真正提供这个变量的定义。

既然这里只有声明，那么我们自然还需要在类外提供一次定义，让程序拥有对应的变量实体。

从机器处理程序的角度来看，这种声明与定义分离的方式，与传统的编译、链接机制十分契合。

但是，从程序员的角度来看，这种设计就不那么自然了。

静态数据成员在逻辑上属于类，我们却需要将它的声明和定义分散在两个位置。对于一些简单的静态变量，这种额外的定义步骤尤其显得繁琐。

因此，C++17 引入了内联变量（inline variables），允许我们直接在类内完成静态数据成员的定义和初始化：

```cpp
class A {
private:
    inline static int _totalCreatedCount = 0;
    inline static int _liveObjectCount = 0;
};
```

从使用者的角度来看，我们可以将这种新写法理解为一种语法糖：它让代码的组织方式更加符合人的直觉，改善了编程体验。

这种写法还涉及内联变量的定义规则，稍后在标准版本的补充部分再展开。

#### 为什么通常把类外定义放在 `.cpp` 中？

这是另一个问题，需要与前面讨论的“为什么必须在类外定义”区分开来。

从代码组织的习惯来看，`.h` 文件通常负责提供声明，`.cpp` 文件则负责提供相应的定义。

不过，这只是一种常见的组织方式，并不意味着头文件在语法上不能包含定义。

真正需要考虑的是头文件的包含机制，以及由此可能引发的 ODR 问题。

我们知道，编译器在处理源文件时，会进行预处理，其中 `#include` 指令会使对应头文件的内容进入当前翻译单元。

假设我们直接在 `A.h` 中定义静态数据成员：

```cpp
#pragma once
class A {
private:
    static int _totalCreatedCount;
};
int A::_totalCreatedCount = 0;
```

如果多个 `.cpp` 文件都包含了这个头文件，那么经过预处理，不同的翻译单元中就会分别出现同一个静态数据成员的定义。

虽然 `#pragma once` 可以避免同一个头文件在单个翻译单元中被重复包含，但它不能阻止不同翻译单元分别包含这个头文件。

于是，采用非内联静态成员时，程序中可能出现多个针对同一个具有外部链接属性的静态数据成员的定义，从而违反单一定义规则。

因此，更合理的组织方式是：

**A.h：只保留静态数据成员的声明。**

```cpp
#pragma once
class A {
private:
    static int _totalCreatedCount;
};
```

**A.cpp：集中提供静态数据成员的定义。**

```cpp
#include "A.h"
int A::_totalCreatedCount = 0;
```

这样，无论多少个源文件包含 `A.h`，它们都只能看到静态数据成员的声明，而真正的定义只存在于 `A.cpp` 所对应的翻译单元中。

所以，对于普通静态数据成员，我们需要区分两个层次：

- **为什么要在类外定义？** 对这里讨论的非内联普通静态数据成员，类内只有声明；发生 ODR 使用时，需要类外定义。

- **为什么建议放在 `.cpp`？** 这是为了避免头文件被多个翻译单元包含时产生重复定义，从而违反 ODR。

前者属于语言规则，后者属于代码组织与链接层面的问题，不能混为一谈。

#### 初始化与对象大小

构造函数的成员初始化列表用于初始化当前对象的非静态数据成员，不能用它初始化静态数据成员。初始化列表还可以初始化基类；基类属于继承的内容，我们后面再学习。这里的两个静态计数器由 `A.cpp` 中的定义初始化，而不随每个 `A` 对象的构造重复初始化。

用 `sizeof(A)` 查看对象大小时，也不会把两个静态计数器的大小算进每个对象。`A` 没有非静态数据成员，在常见实现中，独立的 `A` 对象大小为 1 字节：对象仍需有非零大小，方便区分不同对象。

### 静态成员函数

前面我们通过友元函数读写计数器。由于计数器记录的是整个类的状态，调用这些操作并不需要依赖某个具体对象。能不能把它们放进类里，同时又不要求调用者先创建对象？静态成员函数正好可以做到。

静态成员函数仍然是类的成员，具有相应的访问权限，但调用它不需要对象，也没有隐式的 `this` 指针。因此，它不能直接访问非静态成员或直接调用非静态成员函数；如果显式提供一个对象，仍然可以通过该对象访问相应成员。静态成员函数也不能带非静态成员函数的 `const`、`volatile` 或引用限定符。

下面沿用前面的 `A`，只展示需要调整的部分。把原来的两个友元函数改成公有静态成员函数后，构造、拷贝构造、析构和两个静态数据成员的定义保持不变。

**A.h 中的类声明：**

```cpp
namespace wind {
class A {
public:
    A();
    A(const A& object);
    ~A();

    static void resetCounters();
    static void out(int& totalCreatedCount, int& liveObjectCount);

private:
    static int _totalCreatedCount;
    static int _liveObjectCount;
};

void CopyAndDestroy(const A& source);
void info();
} // namespace wind
```

**A.cpp 中替换原来两个友元函数的定义：**

```cpp
void A::resetCounters() {
    _totalCreatedCount = 0;
    _liveObjectCount = 0;
}

void A::out(int& totalCreatedCount, int& liveObjectCount) {
    totalCreatedCount = _totalCreatedCount;
    liveObjectCount = _liveObjectCount;
}
```

这两段定义仍放在原来的 `namespace wind` 内。同时，`info()` 中的 `out(totalCreatedCount, liveObjectCount)` 要改为 `A::out(totalCreatedCount, liveObjectCount)`。原先命名空间作用域的 `resetCounters` 和 `out` 声明也随之删除：它们现在是类成员，通过 `wind::A::resetCounters()` 和 `wind::A::out(...)` 访问。

也可以通过对象表达式调用静态成员函数，例如 `m.out(total, live)`；不过，这不会使函数获得 `this`。仍然不能在 `m` 等对象存活时调用 `resetCounters()`，否则计数会失真。

class cycle {

### 补充：C++11 之后，静态成员变量有哪些新变化？

以下补充介绍不同标准对静态成员定义和初始化的改进。如果暂时不想展开，可以直接跳过，后面的友元类和内部类不依赖这部分内容。

前面我们已经知道，在 C++11 中，如果一个类拥有普通的静态成员变量，那么通常需要在类内声明，再到类外定义。

例如：

```cpp
class A {
private:
    static int totalCreatedCount;
    static int liveObjectCount;
};
int A::totalCreatedCount = 0;
int A::liveObjectCount = 0;
```

这种写法虽然符合传统的声明与定义分离机制，但从程序员的角度来看，多少有些不方便。

明明这两个变量属于类 `A`，我们却需要把它们的声明和定义分开放置。尤其是一些非常简单的静态变量，我们可能只是希望给它一个初始值，却仍然需要额外编写一次定义。

实际上，随着 C++ 标准不断发展，静态成员变量的使用方式也在逐渐改善。

#### 一、C++11：引入 `static constexpr`

在介绍 C++11 的变化之前，需要先认识一种更早就存在的特殊情况。

对于普通的静态成员变量，我们不能在 C++11 的类内直接初始化：

```cpp
class A {
public:
    static int count = 0; // C++11 中错误
};
```

但是，如果这个变量是 `const` 修饰的整型或枚举类型，那么早在 C++98 中，就已经允许在类内提供初始值。

例如：

```cpp
class A {
public:
    static const int maxCount = 100;
};
```

为什么这种写法可以？

因为它符合语言对非 `volatile` 的整型常量静态成员的特殊规定，并提供了常量表达式作为初始值。

假设我们这样使用它：

```cpp
int arr[A::maxCount]; // A::maxCount 是整型常量表达式
```

编译器在编译时已经知道 `maxCount` 等于 `100`，所以可以直接利用这个值来确定数组长度。

不过，这里有一个容易产生误解的地方：**允许在类内初始化，不代表已经在类内完成了定义。**

这个非内联静态常量成员的类内声明虽然提供了初始值，但如果我们需要取得变量的地址：

```cpp
const int* ptr = &A::maxCount;
```

那么就必须在类外提供定义：

```cpp
const int A::maxCount;
```

原因也不难理解。

前面使用 `maxCount` 确定数组长度时，编译器只需要知道它的值是多少。

但现在我们要获取它的地址，这种使用构成 ODR 使用，因此语言规则要求提供定义。

##### C++11 的改进

C++11 引入了 `constexpr`，让我们能够更明确地表示一个变量的值需要在编译期间确定。

例如：

```cpp
class A {
public:
    static constexpr int maxCount = 100;
    static constexpr double pi = 3.1415926;
};
```

与前面介绍的 `static const` 相比，`static constexpr` 的适用范围更广，不再局限于整型或枚举类型，而是可以用于符合要求的字面值类型。

不过，在 C++11 和 C++14 中，如果发生 ODR 使用，**`static constexpr` 仍然需要类外定义。**

例如：

```cpp
const double* ptr = &A::pi;
```

这里获取了 `pi` 的地址，因此仍然需要在类外定义：

```cpp
constexpr double A::pi;
```

注意，类外定义不需要再写一次 `= 3.1415926`，因为初始值已经在类内提供了。

所以，C++11 虽然扩展了静态常量成员的类内初始化能力，但对于普通静态成员变量，仍然需要遵循原来的类外定义方式。

#### 二、C++17：引入 `inline static`

到了 C++17，情况发生了很大的变化。

我们之前使用的两个对象计数器：

```cpp
class A {
private:
    static int totalCreatedCount;
    static int liveObjectCount;
};
```

在 C++11 中，需要在类外定义：

```cpp
int A::totalCreatedCount = 0;
int A::liveObjectCount = 0;
```

但是从 C++17 开始，我们可以直接这样写：

```cpp
class A {
private:
    inline static int totalCreatedCount = 0;
    inline static int liveObjectCount = 0;
};
```

这样就完成了，不需要再到类外编写定义。

这里新出现的 `inline`，可能会让人联想到以前学过的内联函数。

不过，在这里，我们需要关注的是它对变量定义规则的影响。

##### 为什么加上 `inline` 就可以了？

我们知道，如果把普通静态成员变量的定义放在头文件中，那么当多个源文件包含这个头文件时，经过预处理，每个翻译单元中都会出现相同的变量定义。

在原来的规则下，这可能违反单一定义规则（ODR）。

C++17 引入的内联变量解决了这个问题。

对于这里的内联静态成员，C++ 允许符合规定的定义出现在多个翻译单元中，并让这些定义表示同一个变量。通常我们把同一份类定义放进头文件，各个源文件包含它，这样就能使用同一份定义。

例如，假设 `A.h` 中有：

```cpp
#pragma once
class A {
public:
    inline static int count = 0;
};
```

现在 `main.cpp` 和 `A.cpp` 都包含了 `A.h`。

虽然经过预处理，两个翻译单元中都会出现 `count` 的定义，但由于它是内联变量，这种情况是被允许的。

而且，**程序中并不会因此出现两份相互独立的 `count`。**

无论在哪个翻译单元中访问 `A::count`，操作的都是同一个变量。

因此，C++17 的 `inline static` 同时解决了两个问题：

1. 允许我们直接在类内完成静态成员变量的定义和初始化，省去了额外的类外定义。

2. 允许定义随着头文件进入多个翻译单元，而不会因为这些符合要求的重复定义违反 ODR。

从程序员的角度来看，我们可以把它理解成一种改善编程体验的新写法。

不过，从语言机制来看，它不只是简单的语法糖，还引入了新的定义规则。

#### 三、C++17：`static constexpr` 也不再需要类外定义

前面我们提到，在 C++11 中，即使使用 `static constexpr`，遇到取地址等 ODR-use 场景，仍然需要提供类外定义。

例如：

```cpp
class A {
public:
    static constexpr int maxCount = 100;
};
```

如果在 C++11 中这样使用：

```cpp
const int* ptr = &A::maxCount;
```

我们仍然需要：

```cpp
constexpr int A::maxCount;
```

但是到了 C++17，这一步可以省略。

原因是：**从 C++17 开始，`static constexpr` 静态数据成员自动具有 `inline` 属性。**

也就是说：

```cpp
static constexpr int maxCount = 100;
```

已经具备内联变量的相关性质。

因此，即使我们获取它的地址，也不再需要额外提供类外定义。

这进一步统一了静态常量成员的使用方式。

#### 四、C++20：引入 `constinit`

C++20 又增加了一个新的关键字：`constinit`。

这个关键字解决的问题与前面的 `inline` 有些不同。

前面的 `inline` 主要解决变量在哪里定义，以及多个翻译单元中的定义如何共存。

而 `constinit` 关心的是：**一个具有静态或线程存储期的变量，能否保证在静态初始化阶段完成初始化。**

具有静态存储期的变量，其存储持续整个程序运行期间；对象的生命周期还要结合初始化和销毁来判断。

但这不代表所有静态变量的初始化都一定能够在编译阶段确定。

例如：

```cpp
int GetValue();
class A {
public:
    inline static int count = GetValue();
};
```

这里的 `GetValue()` 是一个普通函数。

由于它的返回值未必能够在编译期间确定，因此 `count` 可能需要在程序启动期间执行动态初始化。

如果我们希望明确禁止这种情况，就可以使用 C++20 的 `constinit`。

例如：

```cpp
class A {
public:
    inline static constinit int count = 0;
};
```

这样，编译器就会检查 `count` 是否能够满足静态初始化的要求。

如果我们试图写成：

```cpp
int GetValue();
class A {
public:
    inline static constinit int count = GetValue(); // 错误
};
```

由于普通的 `GetValue()` 调用不能用于常量初始化，编译器就会报错。

##### `constinit` 与 `constexpr` 有什么区别？

看到这里，可能会产生一个疑问：既然都是对初始化提出要求，那么 `constinit` 和 `constexpr` 有什么不同？

我们直接看两段代码。

```cpp
class A {
public:
    inline static constexpr int count = 0;
};
```

这里的 `count` 是一个常量，初始化完成之后不能再修改。

但是：

```cpp
class A {
public:
    inline static constinit int count = 0;
};
```

这里的 `count` 仍然是普通的可修改变量。

例如：

```cpp
A::count++;
```

这是完全允许的。

因此：

- `constexpr` 变量必须满足常量表达式相关要求；这里的 `count` 是常量，不能修改。

- `constinit` 要求变量完成静态初始化，但不要求变量在初始化之后保持不变。

对于我们之前编写的对象计数器，`constinit` 就是一种可以考虑的选择，因为计数器需要在运行期间不断修改。

不过，`constinit` 并不会自动让静态成员变量成为内联变量。

如果我们仍然希望直接在类内定义普通静态成员变量，就需要保留 `inline`。

#### 五、整理一下各个标准的变化

| C++ 标准 | 静态成员变量的相关变化                                                                              |
| -------- | --------------------------------------------------------------------------------------------------- |
| C++98/03 | 允许符合条件的整型或枚举类型 `static const` 成员在类内初始化                                        |
| C++11    | 引入 `static constexpr`，扩展静态常量成员的类内初始化能力；支持 `thread_local` 静态数据成员         |
| C++14    | 在这里讨论的静态成员变量定义方式上，没有明显的新变化                                                |
| C++17    | 引入 `inline static`，允许普通静态成员变量直接在类内定义；`static constexpr` 自动具有 `inline` 属性 |
| C++20    | 引入 `constinit`，可以要求静态变量必须完成静态初始化                                                |
| C++23    | 在这里讨论的普通静态成员变量定义与初始化方式上，没有类似 C++17 的重大变化                           |

回头看这些标准的发展，我们可以发现一个比较清晰的过程。

早期 C++ 对静态成员变量采用声明与定义分离的方式。这与传统的编译、链接模型相契合，但对于程序员来说，使用起来多少有些繁琐。

C++11 扩展了静态常量成员的类内初始化能力。

C++17 则进一步允许普通静态成员变量直接在类内定义，解决了原先需要额外编写类外定义的问题。

到了 C++20，我们又可以通过 `constinit`，对静态变量的初始化方式提出更明确的要求。

当前使用 C++17 学习，也可以保留传统的类内声明、类外定义写法，以便理解其中的机制。

等到后续使用现代 C++ 编写项目时，就可以根据实际需求采用这些新特性。

参考资料：[cppreference：静态成员](https://zh.cppreference.com/w/cpp/language/static)、[cppreference：constinit](https://zh.cppreference.com/w/cpp/language/constinit)。

数组长度必须是符合要求的常量表达式，并不是因为编译器恰好能算出数值就一定合法。上例的 `A::maxCount` 符合条件，因而可以用于数组长度；普通运行时变量即使碰巧是 100，也不能因此作为标准 C++ 数组的长度。

版本对照：`static const int maxCount = 100;` 从 C++98 起可作数组长度；C++11 起可用 `static constexpr`，但取地址等 ODR 使用在 C++11/14 仍须类外定义；C++17 起 `static constexpr` 隐式内联，不再需要额外定义。

## 友元类与内部类

### 友元类

友元类就是把友元的概念从函数扩展到整个类上。

```cpp
class Time
{
    friend class Date; // Date 可以访问 Time 的私有成员
        public:
    Time(int hour = 0, int minute = 0, int second = 0)
        : _hour(hour)
            , _minute(minute)
            , _second(second)
        {}
    private:
    int _hour;
    int _minute;
    int _second;
};
class Date
{
    public:
    Date(int year = 1900, int month = 1, int day = 1)
        : _year(year)
            , _month(month)
            , _day(day)
        {}
    void SetTimeOfDate(int hour, int minute, int second)
    {
        // 访问 Time 的私有成员
        _t._hour = hour;
        _t._minute = minute;
        _t._second = second;
    }
    private:
    int _year;
    int _month;
    int _day;
    Time _t;
};
```

友元关系是单向的：`Date` 获得访问 `Time` 私有成员的权限，反过来并不成立。友元关系也不会自动传递。友元会让两个类更加紧密地联系在一起，使用时需要考虑这种耦合是否值得。

### 内部类

一个类可以定义在另一个类的内部，这样的类称为嵌套类，也常叫内部类。嵌套类可以访问外层类的私有成员；我们把它与友元类放在一起，看看这两种访问权限的用法。

嵌套类不自带外层类对象，也没有外层类的 `this`：访问外层的非静态成员时仍需要一个外层对象。外层类也不会自动获得访问嵌套类私有成员的权限。嵌套类可以声明在外层类的不同访问区域，其名称对外是否可访问取决于该区域的访问权限。

两个类的类型各自独立：仅仅嵌套声明不会让外层对象自动包含一个嵌套类对象，反之亦然；如果显式定义数据成员，大小仍会受到成员和布局影响。

```cpp
#include <iostream>

class A
{
    private:
    static int k;
    int h = 0;
    public:
    class B // B 可以访问 A 的私有成员
    {
        public:
        void foo(const A& a)
        {
            std::cout << k << std::endl; // 访问静态成员不需要 A 对象
            std::cout << a.h << std::endl; // 访问非静态成员需要 A 对象
        }
    };
};

int A::k = 1;

int main()
{
    A::B b;
    b.foo(A());
    return 0;
}
```

如果嵌套类只是实现细节，可以把它声明在外层类的私有区域，并按需通过外层类的接口提供功能；如果它本身就是公开接口的一部分，也可以声明为公有。

把嵌套类藏在私有区域，倒有点像给实现细节留了一间只供内部使用的小屋。

## 复制消除与编译器优化

下面观察对象作为函数参数和返回值时，构造函数会调用几次。通过输出，我们可以看到 C++ 在某些场景下如何减少中间对象的创建。

```cpp
#include <iostream>

namespace wind
{
	class A
	{
	public:
		A();
		A(const A& object);
		~A();
		void print()const;
         A& operator=(const A& object);
	private:
		int _i;
	};
	void F(A object);
}

wind::A::A()
	:_i(0)
{
	std::cout << "Constructor" << std::endl;
}

wind::A::A(const A& object)
	:_i(object._i)
{
	std::cout << "Copy Constructor" << std::endl;
}

wind::A::~A()
{
	std::cout << "Destructor" << std::endl;
}

void wind::F(A object)
{
	object.print();
}

void wind::A::print()const
{
	std::cout << _i << std::endl;
}

wind::A& wind::A::operator=(const A& object)
{
	_i = object._i;
    return *this;
}

void test3()
{
	wind::A x;
	wind::F(x);
	std::cout << "==================" << std::endl;
	wind::F(wind::A());
	std::cout << "==================" << std::endl;
}

int main()
{
	test3();
	return 0;
}
```

`F(x)` 使用已有对象 `x` 初始化按值参数，因此会调用拷贝构造函数。`F(wind::A())` 则使用 `wind::A()` 创建的临时值初始化参数：在 C++17 中，参数对象直接构造，不需要再拷贝一次。

![image-20241007150257029](https://img.mdwind.online/md/202410071502125.png)

```cpp
void test3()
{
	wind::A x;
	wind::F(x);
	std::cout << "==================" << std::endl;
	wind::F(wind::A());
	std::cout << "==================" << std::endl;
	auto y = wind::A();
	std::cout << "==================" << std::endl;
}
```

`auto y = wind::A();` 也是类似的情况：在 C++17 中直接构造 `y`。即使使用 `-O0`，或者启用 `-fno-elide-constructors`，这里也不会因此多出一次拷贝。

![image-20241007151748047](https://img.mdwind.online/md/202410071517149.png)

```cpp
wind::A test4()
{
	wind::A x;
	return x;
}

int main()
{
	wind::A y = test4();
	return 0;
}
```

`return x;` 返回的是具名局部对象，符合具名返回值优化（NRVO）的条件。NRVO 是允许但不保证的复制消除：实现可以直接在返回对象的位置构造 `x`，即使构造或析构有可观察副作用也可以省略；也可以不做此消除。未消除时，本例会使用拷贝构造函数。

另一方面，`test4()` 的返回结果用来初始化 `y` 时，C++17 不再要求额外创建一个中间对象并拷贝到 `y`。可以用 `-fno-elide-constructors` 观察关闭 NRVO 后的构造过程，但这个选项不能取消 C++17 对上述直接初始化的规定。

![image-20241007152411802](https://img.mdwind.online/md/202410071524872.png)

我们也在 Clang 21、C++17 和 `-O0` 的调试构建中尝试了这些例子，得到了相似的构造与析构结果。`-O0` 并不意味着所有对象都要按照直觉中的步骤逐一构造：前两个例子中的直接构造来自 C++17 的语言规则，而具名返回值优化则是编译器允许进行的复制消除，在 `-O0` 下也可能发生。
