## 静态成员

### 静态成员变量

类中的成员变量可以使用`static`修饰，使之成为静态成员变量。与普通的成员变量不同，静态成员变量存储在静态区而不是对象中。由于静态成员变量不存储在某个具体的对象中，所以它是能被所有对象共享的成员变量(前面一句和后面一句都是对的, 但是没有这么强的因果关系)，这一特性使得它常被用来统计类的整体状态。

看下面一道题目：实现一个类，这个类中包含着若干接口，可以输出已经实例化的对象个数和正在使用的对象个数。

我们知道，对象的实例化无非依靠两个函数：构造函数和拷贝构造函数；对象的销毁只依靠一个函数：析构函数。我们可以定义一个静态变量，去计数两个构造函数的调用次数，即可得到已经实例化的对象个数；然后再通过同样的方法计数析构函数的调用次数，拿已经实例化的对象个数减去已经析构的对象个数即可得到正在使用的对象个数。

针对上述代码的第一个讨论：

我们知道，源文件中使用 `#include` 包含头文件时，预处理器会把头文件的内容展开到包含位置。经过预处理后，原本分散在源文件和头文件中的声明、定义和调用等内容，就进入了同一份供编译器处理的代码。

这份经过预处理、交给编译器编译的代码，称为**翻译单元**。一个源文件通常对应一个翻译单元；多个源文件各自经过预处理和编译，之后再由链接器将它们产生的目标文件组合起来。

虽然声明和调用进入了同一个翻译单元，但这并不意味着编译器处理调用时，只需要随意地从整份代码中找一个同名声明。

可以先建立一个近似的模型：编译器沿着翻译单元处理代码。当它遇到一条声明时，会分析并记录这条声明提供的信息，例如名字、类型、所属作用域，以及它与其他声明之间的关系。此时，编译器并不知道后面是否一定会用到这个名字，但这些信息需要被保留下来，以便后续分析使用。

例如：

```
int global_value;

namespace wind
{
    void init();

    class Date
    {
    private:
        int year_;
    };
}
```

从作用域的角度看，我们可以把其中的关系想象成一种层级结构：

```
全局作用域
├── global_value
└── 命名空间 wind
    ├── 函数 init
    └── 类 Date
        └── 成员 year_
```

在这个模型中，全局作用域里既有直接声明的东西，也有命名空间；命名空间里可以有函数、类，也可以有更深一层的命名空间；类里面又有自己的成员。这样组织之后，当后面需要查找某个名字时，就可以结合名字所在的位置和限定范围，确定应该考虑哪些声明。

不过，这只是从**检索和作用域关系**出发建立的直观模型，并不是说编译器内部一定使用了这样一棵树。实际编译器为了完成语法分析、类型检查、名字查找、生成代码等不同工作，很可能同时使用多种数据结构，从不同角度记录和组织同一份代码的信息。

数据结构没有脱离用途的“最好”。需要完成的操作不同，适合采用的组织方式也会不同。这里用树状结构来理解层级关系，是根据已有的计算机知识作出的合理推测；具体编译器怎样实现，还需要查阅它的源码或相关资料才能确认。

另外，“沿着翻译单元处理”适合用来建立初步认识，但不必把它理解为编译器只能从头到尾扫描一次、绝不能回头。编译器内部可以分阶段处理信息；C++ 对某些位置的名字可见性也有特殊规则。我们目前关注的是：**声明提供的信息会被编译器记录和组织起来，后续分析代码时再按照语言规则使用它们。**

当编译器处理到函数调用时，它就需要利用这些信息，找到调用所指向的函数声明。例如：

```
wind::init();
```

这里写出了 `wind::`，编译器就按照限定名查找的规则，在 `wind` 命名空间中查找 `init`。它不会因为翻译单元里其他命名空间也有名为 `init` 的函数，就把它们全部拿出来参与这次查找。

换句话说，**名字查找有确定的规则和范围**。我们可以把编译器内部的组织方式想象成有助于局部检索，但语言规则首先决定的是哪些声明有资格被找到；具体怎样高效实现，则由编译器决定。

如果找到多个同名函数，编译器还需要结合实参类型进行重载决议，从候选函数中选择合适的版本；如果找不到可用函数，或者无法选出唯一的最佳函数，就会报错。

## 友元声明为什么还需要在类外再写一次

理解名字查找之后，再看这段代码：

```
namespace wind
{
    class a
    {
        friend void init();
    };

    void init();
}
```

类内的这条声明：

```
friend void init();
```

声明了函数 `init`，同时赋予它访问类 `a` 私有成员的权限。虽然声明写在类里面，但这里声明的 `init` 并不是 `a` 的成员函数，它属于外层的 `wind` 命名空间。

不过，友元声明有一条特殊的名字查找规则：如果一个函数首次出现在类内的友元声明中，那么它的名字不会因此自动对普通名字查找可见。

也就是说，编译器处理类定义时，已经记录了这个函数以及它与 `a` 的友元关系；但之后遇到：

```
wind::init();
```

不能仅靠那条类内友元声明，通过普通的限定名查找找到它。

因此，我们在 `wind` 命名空间中再声明一次：

```
void init();
```

这样，`init` 的名字就能够被普通查找找到。后面的 `wind::init()` 可以直接在 `wind` 中找到这条声明；至于 `init` 为什么有权访问 `a` 的私有成员，依据仍然是类内的友元声明。

两条声明对应的是**同一个函数**，不会因为写了两次就产生两个函数。它们分别建立了友元关系，并让函数名对普通查找可见。

这也说明，我们以前对声明的理解可以再扩展一步：同一个函数可以有多条声明，声明所处的位置和写法不同，产生的作用也可能不同。所以，说这里存在重复声明是对的，但重复声明不一定多余。

## 为什么 `Date` 的流运算符没有类外声明也能使用

并非所有首次在类内声明的友元函数，都必须在类外再声明一次。函数调用还有一种补充查找方式，叫作**实参依赖查找（ADL）**：编译器可以根据实参的静态类型，确定相关的查找范围，寻找候选函数。

例如：

```
namespace wind
{
    class Date
    {
        friend std::ostream& operator<<(std::ostream& out,
                                        const Date& d);
    };
}
```

当外部代码使用：

```
wind::Date d;
std::cout << d;
```

编译器知道 `d` 的静态类型是 `wind::Date`。在处理 `<<` 时，实参依赖查找会考虑与 `Date` 关联的范围，并且有一条特殊规则允许它找到关联类中声明的友元函数。于是，即使头文件中没有再写一条类外声明，编译器仍然可以找到这个 `operator<<`。

对比最初的两个友元：

```
friend void init();
friend void out(int& ed, int& ing);
```

`init()` 没有实参，`out(...)` 的实参都是内置类型。调用它们时，编译器无法根据这些实参关联到类 `a`，也就不能通过这条路径找到类内声明的友元。因此，如果希望外部代码通过普通方式调用它们，就需要在命名空间作用域补充声明。

这里的普通查找、实参依赖查找和重载决议都是**编译期间**的工作。函数被选定后，运行时不需要再按照这些规则重新搜索声明。

## 问题一：为什么 C++11 及更早的标准要求静态数据成员在类外定义？

在 C++11 及更早的标准中，对于普通的静态数据成员，我们通常需要先在类内声明，再到类外提供定义。

```
class A{private:    static int _totalCreatedCount;    static int _liveObjectCount;};// 类外定义int A::_totalCreatedCount = 0;int A::_liveObjectCount = 0;
```

为什么要这样规定？

我认为，从传统的编译、链接模型来看，这种设计其实相当自然。

类的定义负责描述一个类拥有哪些成员。对于普通的非静态数据成员，其存储空间属于具体的类对象；而静态数据成员则不同，它们独立于具体对象存在，由同一个类的所有对象共享。

因此，类内的静态数据成员声明，可以理解成一种类似 `extern` 的声明：它告诉编译器，这个类存在这样一个静态变量，明确了变量的名称、类型及其所属的类，但并没有真正提供这个变量的定义。

既然这里只有声明，那么我们自然还需要在类外提供一次定义，让程序拥有对应的变量实体。

从机器处理程序的角度来看，这种声明与定义分离的方式，与传统的编译、链接机制十分契合。

但是，从程序员的角度来看，这种设计就不那么自然了。

静态数据成员在逻辑上属于类，我们却需要将它的声明和定义分散在两个位置。对于一些简单的静态变量，这种额外的定义步骤尤其显得繁琐。

因此，C++17 引入了内联变量（inline variables），允许我们直接在类内完成静态数据成员的定义和初始化：

```
class A{private:    inline static int _totalCreatedCount = 0;    inline static int _liveObjectCount = 0;};
```

从使用者的角度来看，我们可以将这种新写法理解为一种语法糖：它让代码的组织方式更加符合人的直觉，改善了编程体验。

当然，从语言机制来看，这并非单纯地将类外定义移动到类内。`inline` 还改变了相关的单一定义规则（ODR），允许满足特定条件的定义出现在多个翻译单元中，并共同表示同一个变量实体。

## 问题二：为什么通常建议将静态数据成员的类外定义放在 `.cpp` 中，而不是 `.h` 中？

这是另一个问题，需要与前面讨论的“为什么必须在类外定义”区分开来。

从代码组织的习惯来看，`.h` 文件通常负责提供声明，`.cpp` 文件则负责提供相应的定义。

不过，这只是一种常见的组织方式，并不意味着头文件在语法上不能包含定义。

真正需要考虑的是头文件的包含机制，以及由此可能引发的 ODR 问题。

我们知道，编译器在处理源文件时，会进行预处理，其中 `#include` 指令会使对应头文件的内容进入当前翻译单元。

假设我们直接在 `A.h` 中定义静态数据成员：

```
#pragma onceclass A{private:    static int _totalCreatedCount;};int A::_totalCreatedCount = 0;
```

如果多个 `.cpp` 文件都包含了这个头文件，那么经过预处理，不同的翻译单元中就会分别出现同一个静态数据成员的定义。

虽然 `#pragma once` 可以避免同一个头文件在单个翻译单元中被重复包含，但它不能阻止不同翻译单元分别包含这个头文件。

于是，在 C++11 的规则下，程序中可能出现多个针对同一个具有外部链接属性的静态数据成员的定义，从而违反单一定义规则（One Definition Rule，ODR）。

因此，更合理的组织方式是：

**A.h：只保留静态数据成员的声明。**

```
#pragma onceclass A{private:    static int _totalCreatedCount;};
```

**A.cpp：集中提供静态数据成员的定义。**

```
#include "A.h"int A::_totalCreatedCount = 0;
```

这样，无论多少个源文件包含 `A.h`，它们都只能看到静态数据成员的声明，而真正的定义只存在于 `A.cpp` 所对应的翻译单元中。

所以，对于普通静态数据成员，我们需要区分两个层次：

- **为什么要在类外定义？** 这是 C++11 及更早标准对普通静态数据成员的语言规定，涉及声明与定义的区别。

- **为什么建议放在** `**.cpp**`**？** 这是为了避免头文件被多个翻译单元包含时产生重复定义，从而违反 ODR。

前者属于语言规则，后者属于代码组织与链接层面的问题，不能混为一谈。

```cpp
// A.h
#pragma once

namespace wind {
class A {
    // 为静态成员变量的值进行重置
    friend void resetCounters();

    // 读取全局静态变量， 然后对外输出
    friend void out(int& ed, int& ing);

   public:
    A();
    A(const A& object);
    ~A();

   private:
    static int _totalCreatedCount;  // 累计实例化的对象总数，包括已经析构的对象。
    static int _liveObjectCount;    // 当前仍然存活的对象数量
};

void resetCounters();
void out(int& totalCreatedCount, int& liveObjectCount);
void CopyAndDestroy(const A& source);
void info();
}  // namespace wind

// A.cpp
#include "A.h"

#include <iostream>

namespace wind {
// 在C++11及其之前， 类中全局变量
// 的定义及初始化放在类外
int A::_totalCreatedCount = 0;
int A::_liveObjectCount = 0;

A::A() {
    _totalCreatedCount++;
    _liveObjectCount++;
}

A::A(const A& object) {
    (void)object;
    _totalCreatedCount++;
    _liveObjectCount++;
}

A::~A() {
    _liveObjectCount--;
}

void resetCounters() {
    A::_totalCreatedCount = 0;
    A::_liveObjectCount = 0;
}

// 使用这种输出型参数， 没有别的特殊意思
// 只是想少写一个函数--用两个函数分别返回
// 也是完全没有问题的
void out(int& totalCreatedCount, int& liveObjectCount) {
    totalCreatedCount = A::_totalCreatedCount;
    liveObjectCount = A::_liveObjectCount;
}

void CopyAndDestroy(const A& source) {
    // 常引用暂时延长了匿名对象的生命周期
    // 双计数加1
    std::cout << "3" << std::endl;
    info();

    A tmp = source;

    std::cout << "4" << std::endl;
    // 使用拷贝构造再加1
    info();

    (void)tmp;
}

void info() {
    static int totalCreatedCount;
    static int liveObjectCount;
    wind::out(totalCreatedCount, liveObjectCount);
    std::cout << "已经实例化的对象个数：" << totalCreatedCount << std::endl;
    std::cout << "目前还存在的对象个数：" << liveObjectCount << std::endl;
}
}  // namespace wind

// main.cpp
#include <iostream>

#include "A.h"

void test1() {
    std::cout << "1" << std::endl;
    // 一开始, 还没有任何实例化
    // 所以计数都为0
    wind::info();

    wind::A m;
    wind::A n;

    std::cout << "2" << std::endl;
    // 此处这里由通过无参构造进行了两次实例化
    wind::info();
    wind::CopyAndDestroy(wind::A());

    {
        wind::A o;
        std::cout << "5" << std::endl;
        // 匿名对象和CopyAndDestroy中局部对象析构
        // 存在减去2
        wind::info();
    }

    std::cout << "6" << std::endl;
    // 局部变量析构， 存在减去1
    wind::info();

    wind::A p;
    wind::A q;

    std::cout << "7" << std::endl;
    // 再无参构造两次
    wind::info();
}

int main() {
    test1();
    std::cout << "8" << std::endl;
    // 没有存在的了
    wind::info();
    return 0;
}
```

### 静态成员函数

可能会有人好奇：为什么在 `test.h` 的末尾要再次声明函数 `init` 和 `out`？先别急，后面会详细解释（下文中关于友元的解释有点讨论的意思， 但还不够全面， 没有讨论那么令人信服， 所以我们依旧以讨论的讲法为准， 不过我认为旧文中的顺序结构是不自然的， 感觉在跳过来跳过去， 我希望你 gpt 在重新进行整理的时候， 能以更流程的逻辑来进行写作）。这里对 `init` 和 `out` 进行友元声明，主要是为了让这两个函数访问类中私有的成员变量 `_used` 和 `_using`。将它们写成成员函数似乎不太合适，因为从功能上来看，这两个函数关注的是整个类的运行状态，而不是个别对象的状态。

如果将它们写成成员函数，虽然可以通过 `this` 指针（如 `this->_used` 或 `(*this)._using`）访问这两个静态成员变量，但这样写总让人感觉不太自然。因此，最终选择将它们写成友元函数。

然而，友元函数的使用会提升类之间的耦合度，通常建议尽量避免使用友元函数。那么，有什么替代方案呢？

当然是有的，这就是我们接下来要讲的内容——静态成员函数。

这里插入有关 C++ 11 后新标准对于静态成员变量定义的新变化

下面这版适合直接放进文章里作为补充资料。我保留了各个标准之间的变化，但会重点解释：为什么要引入这些新写法，它们解决了什么问题，以及与原来的写法有什么区别。

# C++11 之后，静态成员变量有哪些新变化？

前面我们已经知道，在 C++11 中，如果一个类拥有普通的静态成员变量，那么通常需要在类内声明，再到类外定义。

例如：

```
class A{private:    static int totalCreatedCount;    static int liveObjectCount;};// 类外定义int A::totalCreatedCount = 0;int A::liveObjectCount = 0;
```

这种写法虽然符合传统的声明与定义分离机制，但从程序员的角度来看，多少有些不方便。

明明这两个变量属于类 `A`，我们却需要把它们的声明和定义分开放置。尤其是一些非常简单的静态变量，我们可能只是希望给它一个初始值，却仍然需要额外编写一次定义。

实际上，随着 C++ 标准不断发展，静态成员变量的使用方式也在逐渐改善。

## 一、C++11：引入 `static constexpr`

在介绍 C++11 的变化之前，需要先认识一种更早就存在的特殊情况。

对于普通的静态成员变量，我们不能在 C++11 的类内直接初始化：

```
class A{public:    static int count = 0; // 错误};
```

但是，如果这个变量是 `const` 修饰的整型或枚举类型，那么早在 C++98 中，就已经允许在类内提供初始值。

例如：

```
class A{public:    static const int maxCount = 100;};
```

为什么这种写法可以？

因为 `maxCount` 是一个整型常量，而且它的值在编译期间就能够确定。

假设我们这样使用它：

```
int arr[A::maxCount];
```

编译器在编译时已经知道 `maxCount` 等于 `100`，所以可以直接利用这个值来确定数组长度。

不过，这里有一个容易产生误解的地方：**允许在类内初始化，不代表已经在类内完成了定义。**

在 C++11 及更早的标准中，这条声明虽然提供了初始值，但如果我们需要取得变量的地址：

```
const int* ptr = &A::maxCount;
```

那么就必须在类外提供定义：

```
const int A::maxCount;
```

原因也不难理解。

前面使用 `maxCount` 确定数组长度时，编译器只需要知道它的值是多少。

但现在我们要获取它的地址，这就要求程序中确实存在一个对应的变量实体。

这种要求变量必须存在定义的使用方式，涉及我们之前讨论过的 ODR-use。

### C++11 的改进

C++11 引入了 `constexpr`，让我们能够更明确地表示一个变量的值需要在编译期间确定。

例如：

```
class A{public:    static constexpr int maxCount = 100;    static constexpr double pi = 3.1415926;};
```

与前面介绍的 `static const` 相比，`static constexpr` 的适用范围更广，不再局限于整型或枚举类型，而是可以用于符合要求的字面值类型。

不过，在 C++11 中，`**static constexpr**` **仍然不能彻底省略类外定义。**

例如：

```
const double* ptr = &A::pi;
```

这里获取了 `pi` 的地址，因此仍然需要在类外定义：

```
constexpr double A::pi;
```

注意，类外定义不需要再写一次 `= 3.1415926`，因为初始值已经在类内提供了。

所以，C++11 虽然扩展了静态常量成员的类内初始化能力，但对于普通静态成员变量，仍然需要遵循原来的类外定义方式。

## 二、C++17：引入 `inline static`

到了 C++17，情况发生了很大的变化。

我们之前使用的两个对象计数器：

```
class A{private:    static int totalCreatedCount;    static int liveObjectCount;};
```

在 C++11 中，需要在类外定义：

```
int A::totalCreatedCount = 0;int A::liveObjectCount = 0;
```

但是从 C++17 开始，我们可以直接这样写：

```
class A{private:    inline static int totalCreatedCount = 0;    inline static int liveObjectCount = 0;};
```

这样就完成了，不需要再到类外编写定义。

这里新出现的 `inline`，可能会让人联想到以前学过的内联函数。

不过，在这里，我们需要关注的是它对变量定义规则的影响。

### 为什么加上 `inline` 就可以了？

我们知道，如果把普通静态成员变量的定义放在头文件中，那么当多个源文件包含这个头文件时，经过预处理，每个翻译单元中都会出现相同的变量定义。

在原来的规则下，这可能违反单一定义规则（ODR）。

C++17 引入的内联变量解决了这个问题。

对于符合要求的内联变量，C++ 允许它的定义出现在多个翻译单元中，并保证这些定义表示的是同一个变量实体。

例如，假设 `A.h` 中有：

```
#pragma onceclass A{public:    inline static int count = 0;};
```

现在 `main.cpp` 和 `test.cpp` 都包含了 `A.h`。

虽然经过预处理，两个翻译单元中都会出现 `count` 的定义，但由于它是内联变量，这种情况是被允许的。

而且，**程序中并不会因此出现两份相互独立的** `**count**`**。**

无论在哪个翻译单元中访问 `A::count`，操作的都是同一个变量。

因此，C++17 的 `inline static` 同时解决了两个问题：

1. 允许我们直接在类内完成静态成员变量的定义和初始化，省去了额外的类外定义。

2. 允许定义随着头文件进入多个翻译单元，而不会因为这些符合要求的重复定义违反 ODR。

从程序员的角度来看，我们可以把它理解成一种改善编程体验的新写法。

不过，从语言机制来看，它不只是简单的语法糖，还引入了新的定义规则。

## 三、C++17：`static constexpr` 也不再需要类外定义

前面我们提到，在 C++11 中，即使使用 `static constexpr`，遇到取地址等 ODR-use 场景，仍然需要提供类外定义。

例如：

```
class A{public:    static constexpr int maxCount = 100;};
```

如果在 C++11 中这样使用：

```
const int* ptr = &A::maxCount;
```

我们仍然需要：

```
constexpr int A::maxCount;
```

但是到了 C++17，这一步可以省略。

原因是：**从 C++17 开始，**`**static constexpr**` **静态数据成员自动具有** `**inline**` **属性。**

也就是说：

```
static constexpr int maxCount = 100;
```

已经具备内联变量的相关性质。

因此，即使我们获取它的地址，也不再需要额外提供类外定义。

这进一步统一了静态常量成员的使用方式。

## 四、C++20：引入 `constinit`

C++20 又增加了一个新的关键字：`constinit`。

这个关键字解决的问题与前面的 `inline` 有些不同。

前面的 `inline` 主要解决变量在哪里定义，以及多个翻译单元中的定义如何共存。

而 `constinit` 关心的是：**一个具有静态或线程存储期的变量，能否保证在静态初始化阶段完成初始化。**

我们知道，静态变量的生命周期通常贯穿整个程序运行过程。

但这不代表所有静态变量的初始化都一定能够在编译阶段确定。

例如：

```
int GetValue();class A{public:    inline static int count = GetValue();};
```

这里的 `GetValue()` 是一个普通函数。

由于它的返回值未必能够在编译期间确定，因此 `count` 可能需要在程序启动期间执行动态初始化。

如果我们希望明确禁止这种情况，就可以使用 C++20 的 `constinit`。

例如：

```
class A{public:    inline static constinit int count = 0;};
```

这样，编译器就会检查 `count` 是否能够满足静态初始化的要求。

如果我们试图写成：

```
int GetValue();class A{public:    inline static constinit int count = GetValue();};
```

由于普通的 `GetValue()` 调用不能用于常量初始化，编译器就会报错。

### `constinit` 与 `constexpr` 有什么区别？

看到这里，可能会产生一个疑问：既然都是对初始化提出要求，那么 `constinit` 和 `constexpr` 有什么不同？

我们直接看两段代码。

```
class A{public:    inline static constexpr int count = 0;};
```

这里的 `count` 是一个常量，初始化完成之后不能再修改。

但是：

```
class A{public:    inline static constinit int count = 0;};
```

这里的 `count` 仍然是普通的可修改变量。

例如：

```
A::count++;
```

这是完全允许的。

因此：

- `constexpr` 要求对象满足常量表达式相关规则，`constexpr` 变量本身也不能被修改。

- `constinit` 要求变量完成静态初始化，但不要求变量在初始化之后保持不变。

对于我们之前编写的对象计数器，`constinit` 就是一种可以考虑的选择，因为计数器需要在运行期间不断修改。

不过，`constinit` 并不会自动让静态成员变量成为内联变量。

如果我们仍然希望直接在类内定义普通静态成员变量，就需要保留 `inline`。

## 五、整理一下各个标准的变化

| C++ 标准 | 静态成员变量的相关变化                                                                              |

| C++11    | 引入 `static constexpr`，扩展静态常量成员的类内初始化能力；支持 `thread_local` 静态数据成员         |

回头看这些标准的发展，我们可以发现一个比较清晰的过程。

早期 C++ 对静态成员变量采用声明与定义分离的方式。这与传统的编译、链接模型相契合，但对于程序员来说，使用起来多少有些繁琐。

对于目前正在使用 C++11 学习静态成员变量的阶段，仍然可以保留传统的类内声明、类外定义写法，以便理解其中的机制。

## 友元

### 友元函数

我们之前稍微提及了友元函数。友元函数是定义在类外的普通函数，但由于它在类中进行了友元声明，所以可以访问类中的私有成员变量。友元函数不是类的成员函数，所以没有`this`指针，自然也没有用`const`进行修饰的用法。友元声明可以写在类中的任意位置，不受访问限定符的限制。

下面我们来讨论友元函数的域突破问题。

回到之前提到的疑问：为什么在 `test.h` 的末尾要再次声明函数 `init` 和 `out`？这涉及到域的突破问题。类和命名空间类似，都是一种域。域的突破有两种方式：直接突破和间接突破。比如，`wind::Date d;` 是直接突破；而 `d.print()` 则是间接突破。尽管我没有明确指出要调用 `Date` 中的成员函数 `print`，但对象 `d` 已经突破了两层域，而 `d.print()` 会被编译器转换为 `print(&d)`，其中 `&d` 是 `this` 指针，它已经突破了两层域，因此可以连带着 `print()` 也突破这两层域。

在上文中，`init` 和 `out` 函数比较特殊。一方面，它们没有与类相关的参数，比如类本身、类的指针或引用，因此无法通过参数间接突破域；另一方面，友元声明是写在类中的，虽然友元声明也是一种函数声明，但若想让编译器识别这个函数声明，必须突破两层域：外层的命名空间 `wind` 和内层的类域 `a`。然而，是否可以使用 `wind::a::init()` 这样的写法呢？不行，因为 `init` 是友元函数，并不是类的成员函数，所以无法这样调用。因此，我们只能额外再声明一次，以帮助它突破类域，否则将无法被识别和调用。

前面我们的友元函数示例，是个运算符重载函数，运算符重载函数必须有一个和类有关的参数，所以，看起来就像不用突破域一样，实际它不是不用突破域，而是突破域的过程是间接的，无法直接看到而已。

### 友元类

友元类就是把友元的概念从函数扩展到整个类上。

```cpp

{
    friend class Date; // 声明日期类为时间类的友元类，则在日期类中就直接访问Time类中的私有成
    员变量
        public:
    Time(int hour = 0, int minute = 0, int second = 0)

            , _minute(minute)
```

注意友元类是单向的。`Time`并不能直接访问`Date`中的成员变量。友元类实在是太破坏封装了，极大地增加了耦合度，不到万不得已不要用。

### 内部类

为什么要把内部类归到友元里呢？因为内部类天然具备友元的特性。私有和公有的概念主要是针对类域外的事物而言，在类域内部并不存在这样的区分。当一个类定义在另一个类的内部时，内部类能够自由访问外部类的成员变量。

这种关系与友元类相似，但它是单向的：内部类可以访问外部类的成员变量，但外部类无法访问内部类的成员变量。此外，内部类可以在外部类的任意位置定义。

值得注意的是，内部类和外部类是相互独立的类，可以使用 `sizeof` 来计算它们的大小，它们之间是完全独立的。

```cpp
class A
{
    private:
    static int k;
    int h;
    public:
    class B // B天生就是A的友元
    {
        public:
        void foo(const A& a)
        {
            cout << k << endl;//OK
            cout << a.h << endl;//OK
        }
    };
};

int A::k = 1;

int main()
{
    A::B b;
    b.foo(A());
    return 0;
}
```

稍微想了一下，为了更好地封账，应该把内部类写在外部类的私有里，这样可以防止外部直接访问。同时，可以在外部类中提供一个接口，以便外部能够安全地查看内部类的信息。这样的做法不仅增强了封装性，还能有效控制对内部类的访问权限。

## 编译器的优化

有些编译器会对代码逻辑进行一定的优化，减少多余步骤。它只合并连续的步骤，避免优化过度出错。(这种(具体是那种)语法上的优化, 是无关乎优化等级的)

```cpp
namespace wind
{
	class A
	{
	public:
		A();
		A(const A& object);
		~A();
		void print()const;
         A& operator=(const A& opject);
	private:
		int _i;
	};
	void F(A opject);
}

wind::A::A()
	:_i(0)
{
	std::cout << "Constructor" << std::endl;
}

wind::A::A(const A& opject)
	:_i(0)
{
	std::cout << "Copy Constructor" << std::endl;
}

wind::A::~A()
{
	std::cout << "Destructor" << std::endl;
}

void wind::F(A opject)
{
	opject.print();
}

void wind::A::print()const
{
	std::cout << _i << std::endl;
}

wind::A& wind::A::operator=(const A& opject)
{
	_i = opject._i;
    return *this;
}

void test3()
{
	wind::A x;
	F(x);
	std::cout << "==================" << std::endl;
	F(wind::A());
	std::cout << "==================" << std::endl;
}

int main()
{
	test3();
	return 0;
}
```

本来逻辑应该是先进拷贝构造，构造出匿名对象，然后拷贝构造出一个对象给`F`，但编译器觉得这种逻辑太麻烦了，于是就会直接在`F`里构造对象。

```cpp
void test3()
{
	wind::A x;
	F(x);
	std::cout << "==================" << std::endl;
	F(wind::A());
	std::cout << "==================" << std::endl;
	auto y = wind::A();
	std::cout << "==================" << std::endl;
}
```

 本来应该先构造匿名对象，再拷贝构造的，但编译器一步优化成对`y`进行构造。

```cpp
wind::A test4()
{
	wind::A x;
	return x;
}

int main()
{
	wind::A y = test4();
	return 0;
}
```

本来应该先在`test4`里构造，然后再拷贝构造出一个临时变量，然后再把临时变量拷贝到`main`里，然后再拷贝构造`y`；然后编译器一步到位，直接对`y`构造。
